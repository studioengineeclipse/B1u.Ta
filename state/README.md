# `state/` — runtime state

Everything here is produced by running the system, not authored. Most of it is gitignored, and the
reasoning differs per file.

| Path | Committed? | Why |
|---|---|---|
| `participation.json` | no | Regenerated by `rake probe` from this environment's toolchains. Committing it would freeze one machine's answer as though it were the repository's. |
| `packages/` | no | Derived from the IR and recomputable. Every planning run would otherwise dirty the tree. |
| `ledger.jsonl` | no | Per-deployment history. See below. |
| `executive-handoff.md` | no | Regenerated by `rake report` from the three above. |

## Why the ledger is not committed

The ledger is history, and discarding history is exactly what `SPEC/30` exists to prevent — so
gitignoring it deserves a reason rather than a shrug.

It is **per-deployment** history. The records describe what *this* installation did: its process
ids, its attempt identities, its wall-clock times. Another clone did not perform those actions, and
a chain merged across clones would be a chain nobody could verify — two histories interleaved by
git, with sequence numbers colliding and links pointing at records from a different machine.

So the ledger is local, append-only, and verified locally:

```sh
b1ledger verify        # walk the chain, recompute every digest and link
b1ledger show          # one line per record
```

If a deployment needs durable audit history, the ledger file is what to back up — not what to
commit. Its integrity guarantee is tamper-*evidence* within one file, and that guarantee does not
survive a merge.

## Regenerating everything

```sh
rake verify    # build, test, conform, probe -> participation.json
b1 plan <ir>   # -> packages/, and one ledger record
rake report    # -> executive-handoff.md
```
